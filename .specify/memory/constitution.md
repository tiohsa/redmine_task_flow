# Redmine Task Flow プロジェクト憲章

## 基本原則

### I. 機能の公開入口と依存方向

- 新規機能のフロントエンドでは、UI・ストア → `frontend/src/features/<feature>/index.ts` → ドメインの順に依存させる。
- 新規機能の Rails 側では、コントローラー → `TaskFlow::Features::<Feature>::Public`
  （`app/services/task_flow/features/<feature>/public.rb`）→ ドメインの順に依存させる。
- 他の機能や UI からは対象機能の公開入口を使い、内部実装への直接参照を禁止する。
  機能内の純粋な処理は `internal/domain/` に配置する。依存方向を固定し、内部実装の変更が呼び出し元へ波及するのを防ぐ。

### II. 認証・認可と安全な属性設定

- `TaskFlowsController` は Rails のセッション認証を使い、対象プロジェクトに対する
  `:create_issues_via_flow`、`:add_issues`、`:manage_issue_relations` のすべてをサーバー側で検証する。
  プロジェクトメニューも同じ三つの権限がそろっている場合に表示する。
- Rails の CSRF 保護を維持し、フロントエンドからの更新リクエストには `X-CSRF-Token` を付与する。
  ユーザーの API キーをページ、ログ、テスト、コミットに含めることを禁止する。
- チケット作成時の属性は `Issue#safe_attributes=` を通じて設定し、Redmine 標準の権限制御と無効化フィールドの制御を保つ。

### III. 公開契約の回帰テスト

- バックエンドは Minitest、フロントエンドは Vitest を使う。機能の公開入口やルートを通じて、
  レスポンスの具体値、状態、保存結果、エラーなど、呼び出し元から観測できる結果を検証する。
- 仕様に記載した正常系と、該当する境界値・失敗系を回帰テストで検証する。新規機能では、
  仕様のテスト ID と Vitest または Minitest の該当テスト名の先頭を一致させる。
- テストでの差し替えは外部 I/O 境界に限定する。呼び出しを検証する場合は観測可能な結果も検証する。
  各ケースは 5 検証・40 行以内に収める。
  [テスト品質ルール](../../agents/rules/testing-anti-patterns.md)

### IV. 統合検証と実ブラウザー検証

- プラグインルートで `node verification/verify-cli.mjs` を実行する。`--local` の対象範囲と
  Docker・Playwright の準備は、テスト・検証仕様に従う。
  [テスト・検証仕様](../../docs/06-testing-and-verification.md)
- UI または API の挙動を変更した場合は、単体テストと結合テストに加え、
  `bash verification/start-e2e.sh` で評価用 Redmine（`http://127.0.0.1:3001`）を起動し、実ブラウザーで検証する。
  初期表示、ノード・エッジ操作、ドラッグ＆ドロップ、一括起票の成功時とエラー時の表示、
  再読み込み後の保存結果と下書き復元、権限不足時の挙動を確認する。
- 実行したコマンドと結果を報告し、環境の制約で検証できなかった項目とその理由を明記する。

### V. 仕様の正本の維持

- `docs/` 配下の機能別文書を仕様・設計・テスト仕様の正本とする。
  新規機能や仕様に関わる修正では、実装前に該当する仕様書で受け入れ条件、正常系、該当する境界値・失敗時の挙動、
  必要なテストを確定する。新規機能の仕様は `docs/<feature>/SPEC.md` に記載する。
- 機能の追加や仕様の変更では、該当する仕様書とテストを実装と同じ変更で更新する。
  古くなった記述や不要な仕様ファイルを整理し、正本を実装および検証内容と一致させる。

## 境界とテスト品質の維持

- 境界とテスト品質の既存例外は Ratchet Mode で追跡し、新たな例外の追加を禁止する。
  既存例外を解消した変更では、対応する項目を同じ変更でベースラインから削除する。
  [既存例外のベースライン](../../verification/architecture-baseline.json)
- 同種のレビュー修正が 2 回発生した場合は、静的ルールまたは共通の安全な API に反映する。

## 開発とレビューの手順

- 利用者向けの入口や検証シナリオを変更した場合は、機能マップの対応箇所も更新する。
  [機能マップ](../../verification/feature-map.json)
- 変更レビューでは、依存方向、認証・認可と属性設定、仕様とテスト ID の対応、検証結果、正本の更新を
  変更内容に応じて確認する。検証を実施できなかった場合は、その項目と理由も確認する。
  [開発ガイド](../../AGENTS.md)

## 憲章の運用

- 憲章を改訂する場合は、改訂理由、対象の原則、影響範囲、必要な移行手順を改訂案に記録する。
  レビューで影響と適合性を確認し、承認後に版と最終改訂日を更新する。
- 版番号はセマンティックバージョニングに従う。互換性を失う原則の削除・再定義はメジャー版、
  原則の追加や規則の実質的な拡張はマイナー版、意味を変えない明確化や誤記訂正はパッチ版を上げる。
