# 検証手順 — ノードのチケット属性を一括変更

## 準備

プラグインルートで実行する。Node.js とインストール済みフロントエンド依存、Ruby、Docker Compose、Playwright と Chromium を準備する。[環境と検証 CLI の設定](../06-testing-and-verification.md)

```bash
npm --prefix frontend test
bash verification/run-minitest.sh
node verification/verify-cli.mjs
npm --prefix frontend run build
bash verification/start-e2e.sh
```

評価用 Redmine の `http://127.0.0.1:3001/projects/task-flow-e2e/task_flow` を実ブラウザーで開く。認証情報は検証仕様の評価用アカウントを使う。既にコンテナへアセットを読み込ませている場合は、ビルド後に評価用サービスを再起動する。

```bash
docker compose -f ../../docker-compose.yml -f verification/compose.e2e.yml restart task-flow-e2e
```

評価用プロジェクトに共通の許可ステータスを持つトラッカー、許可ステータスが異なるトラッカー、担当者または対象バージョンを無効化したトラッカーを用意する。変更先に必須リスト型カスタムフィールドを設定し、選択可能な担当者と公開中の対象バージョンを用意する。権限ケースには、3 権限をそれぞれ 1 つだけ欠く評価用ロールと全権限の評価用ロールを用意する。権限取り消しの操作は評価用ロールまたはメンバー割り当てに限定する。

親グループ枠の優先度をチケット上で個別に確認するケースでは、評価用 Redmine の親チケットの優先度を一時的に「子チケットと独立」に設定する。子チケットから算出する設定では、起票後の親の優先度は Redmine の集計結果になる。[Redmine の親チケット優先度](https://github.com/redmine/redmine/blob/7.0.2/app/models/issue.rb#L1371-L1373)

## 実ブラウザーの確認

| シナリオ | 操作と期待結果 |
| --- | --- |
| P1 対象と属性（BNE-01〜05、08、10） | タスク、グループ、未選択の子タスク、依存エッジがあるフローを用意する。キャンバスでタスクを選択した状態からキーボードで起動し、0 件、1 件、2 件の適用可否と選択・解除を確認する。タスクとグループの 4 属性を適用して未選択の子、親子・依存関係、ステータスを比較する。候補の無効化、非互換ノードだけを残したときの件数とステータス両方のエラー、明示解除、無指定、差分なし、取消、全画面での Esc を確認する |
| P1 件数境界（BNE-08） | 既存 v1 JSON 入力でグループを含む有効な 101 ノードのフローを用意する。99 件と 100 件に異なる値を適用し、101 件では件数と上限が表示されて更新されないこと、100 件へ戻して適用できることを確認する |
| P2 履歴・復元（BNE-06） | 変更直後のノードと自動下書きを確認する。Undo 1 回、Redo 1 回の結果を全対象で比較する。再読み込みで編集結果が復元され、変更先で有効なカスタムフィールドだけが残ることを確認する |
| P3 必須項目と起票（BNE-07） | 100 件以下の別フローで必須フィールド付きトラッカーを適用する。適用は成功し、登録は不足を表示して停止する。対象ノードごとに補完して登録し、Redmine チケット上で変更した属性と親子・依存関係を確認する。送信済みの入口も確認する |
| P3 権限取り消しと再試行（BNE-09、11） | 3 種類の不足ロールごとにメニュー非表示と直アクセスの 403 を確認する。別セッションで編集中ユーザーから権限を取り消して一括登録し、権限表示、チケット・関連 0 件、下書きと編集の保持を確認する。権限を戻し、次に管理者の別セッションで対象トラッカーに既定値のない必須項目を追加する。元の編集画面から登録して 422 詳細と作成 0 件を確認し、再読み込みで下書きを復元して必須項目を補完し、再登録する。同じノードに複数の理由が返る 422 では、すべての詳細と下書き保持を確認する。関連の保存段階の失敗・再試行は Minitest の BNE-11 でも検証する |

ストレージ書き込み失敗、適用直前の対象消失、送信中の再適用誘発は Vitest で再現し、失敗後の公開状態と再試行の結果を確認する。実ブラウザーでは既存の初期表示、ノードとエッジ操作、D&D、名前付きフロー保存・復元、下書き復元も確認する。[共通ブラウザーシナリオ](../06-testing-and-verification.md#4-実ブラウザ-e2e-検証シナリオdocker-上の評価用-redmine)

同一ノードへの複数の 422 詳細は、3 件のタスクで 2 本の依存関係を同じタスクに向け、v1 JSON でそれぞれ別 ID の重複エッジを加えて読み込むと再現できる。属性を一括変更してから登録し、重複した依存関係の両方が表示されることを確認する。重複エッジを除いて再登録する。

検証結果に実行コマンド、対象シナリオの成否、環境制約で確認できなかった項目を記録する。検証 CLI の模擬 API スモークと、評価用 DB を使用する認証済み実ブラウザーの結果をそれぞれ記録する。

検証 CLI と認証済み Chrome はポート 3001 に接続した。配信に使うコミット対象の JS/CSS は、検証用ディレクトリに新規ビルドした JS/CSS とバイト単位で一致した。

トラッカーの非互換ステータス、担当者・対象バージョンの候補連動と解除、下書き書き込み失敗、関連の保存途中でのロールバックは、今回の再検証では自動テストで確認した。
