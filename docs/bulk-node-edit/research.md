# 調査結果 — ノードのチケット属性を一括変更

## 機能境界と適用処理

- **決定**　候補と適用可否の判定を `frontend/src/features/bulk-node-edit/index.ts` から公開し、純粋な判定とノード更新案の生成を `internal/domain/` に置く。Zustand は最新状態の取得、下書き保存、履歴の確定を担当する。
- **根拠**　既存の `updateNodeData` はトラッカー変更に伴う既定ステータスへの補正と日程伝播を行い、履歴と下書きをノードごとに更新する。一括適用は 4 属性の変更を全件検証し、既存の履歴上限と自動下書き形式で 1 回の編集として扱う。
- **検討した案**　単一ノード更新の反復はステータス維持・全件適用・Undo 1 回の条件を満たせない。Rails への適用 API 追加は、編集中の操作がブラウザー内で完結する契約を変える。

## 候補と適用前検証

- **決定**　既存 `BootstrapData` の `trackers`、`priorities`、`assignable_users`、`versions` を使う。担当者・対象バージョンは各対象の適用後トラッカーの `disabled_core_fields` を参照する。実際にトラッカーが変わる対象では `allowed_status_ids` への現在ステータスの所属を確認する。
- **根拠**　既存 Bootstrap はプロジェクトと利用者に応じた候補を供給する。表示と適用で純粋な判定を共有し、適用時にストアの最新値で再計算すると、古い表示を起点とする更新を防げる。旧 JSON から残る文字列 ID は差分・所属判定時に数値 ID と同一視する。新規指定は型どおりの ID で検証する。
- **検討した案**　画面での確認だけでは対象消失を扱えない。起票前の全属性検証を適用の条件にすると、新たな必須カスタムフィールドを後から補う利用シナリオを妨げる。

## 保存と失敗時の扱い

- **決定**　変更案を作り、既存の `saveDraftToStorage` で同期保存を 1 回行う。保存成功後にノード、変更した対象の古い検証エラー、履歴を 1 回のストア更新で確定する。
- **根拠**　既存の保存関数は成否を返す。保存に失敗した場合も、直前のノード・履歴・下書きを保持して同じ画面から再試行できる。再読み込み時は既存のサニタイズが現在のトラッカーで無効なカスタムフィールドを除外する。
- **検討した案**　ストア更新後の保存とロールバックは途中状態を購読側へ公開する。既存の共通自動保存は失敗結果を呼び出し元へ返さないため一括適用に必要な拒否を表現できない。

## キーボード操作

- **決定**　ツールバーから標準 `<dialog>` を `showModal()` で開く。ラベル付きチェックボックスとセレクト、見出しによるダイアログ名、件数とエラーの通知を使う。ダイアログを開いている間はキャンバスの全体ショートカットと全画面解除を抑止する。
- **根拠**　ネイティブのモーダルが背景の操作抑止、フォーカス、閉じる操作を担う。既存 `FlowCanvas` の `window` キーハンドラーはタスクノード選択中の Tab / Enter でノードを追加するため、モーダル内および起動ボタンをその処理から除く必要がある。[HTML Standard](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element) [WAI-ARIA モーダルダイアログ](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- **検討した案**　キャンバス上の複数選択は既存の選択モデルに変更が及ぶ。既存の `div` オーバーレイ方式ではフォーカス制御を追加で実装する必要がある。

## 登録拒否とロールバック

- **決定**　既存の登録 API を使い、`postBulkCreate` の応答処理で 403 を権限不足として表示する。JSON に既存のエラー文言があれば使用し、本文なしの 403 には権限不足の文言を用意する。リダイレクトは既存のセッション切れとして処理する。
- **根拠**　Redmine 標準の認可がプラグインの JSON 認可より先に拒否する場合、JSON ルートでも 403 に本文がない経路がある。現在のクライアントは JSON 以外をセッション切れと判定する。起票の属性処理とロールバックは既存の `safe_attributes=` とトランザクションを使い、公開ルートから回帰を検証する。[Redmine 7.0.2 の認可とエラー応答](https://github.com/redmine/redmine/blob/7.0.2/app/controllers/application_controller.rb#L312-L330) [Redmine 7.0.2 の render_error](https://github.com/redmine/redmine/blob/7.0.2/app/controllers/application_controller.rb#L544-L568)
- **検討した案**　Rails の認可フィルターを並べ替えると、他のアクションの拒否経路にも影響する。既存の HTTP ステータスを一括登録クライアントで解釈すれば、サーバー側の認可条件と応答形式を維持できる。
