# SPEC: ノードのチケット属性を一括変更

レビュー用ドラフト

## 1. Goal

- タスクフローに追加済みの複数ノードを選び、トラッカー、ステータス、優先度、担当者、対象バージョン、カスタムフィールドをまとめて変更できるようにする。一括変更の適用後は、通常の編集と同じように下書きに反映し、既存の一括登録で起票できる。

## 2. Non-goals / Out-of-scope

- 起票済み Redmine チケットの更新、複数フローをまたぐ操作、新規ノードの既定値の一括設定。
- 題名、説明、日程、工数、ノード位置、親子関係、依存関係の一括編集。
- キャンバスの選択モデル、単一ノード・エッジの編集方法、既存のカスタムフィールド形式の対応範囲の拡張。

## 3. Acceptance Criteria

- [ ] **AC-01 対象選択** `[ASSUMPTION]` 編集可能なフローにノードが 2 件以上あるとき、ツールバーの「属性を一括変更」から対象選択と属性指定を開ける。各ノードを個別に選択・解除でき、選択件数が表示される。タスクノードと親グループ枠の混在を許可する。親グループ枠の選択で子タスクが自動選択されることはない。対象選択と適用はキーボードでも操作できる。
- [ ] **AC-02 属性の指定** `[ASSUMPTION]` 各標準属性と各カスタムフィールドを個別に変更対象へ追加できる。初期状態は全項目「変更しない」とし、元の値が混在していてもいずれかの値を適用値として自動選択しない。担当者は「未割当」、対象バージョンは「なし」、任意のカスタムフィールドは空欄を明示指定できる。カスタムフィールドはフィールド ID 単位で既存値に反映する。
- [ ] **AC-03 トラッカー連動** ステータスの候補は全対象ノードの適用後トラッカーで許可される値の共通部分とする。トラッカー未指定時はノードごとの現在のトラッカーを使う。許可ステータスが空なら候補も空とする。担当者・対象バージョンは全対象の適用後トラッカーで有効な場合に変更できる。カスタムフィールドは全対象の適用後トラッカーに同じ ID で存在し、現在のユーザーに可視の項目を表示する。トラッカーや対象選択の変更で候補を更新し、すでに指定した値が無効になった場合は該当項目を示して適用を止める。
- [ ] **AC-04 ステータスの補正** `[ASSUMPTION]` トラッカーだけを変更し、現在のステータスが変更先でも許可されるノードはそのステータスを維持する。許可されないノードは変更先の既定ステータスへ切り替え、適用前に補正が発生することを画面に示す。既定ステータスも許可されない場合は適用を止める。有効なステータスが明示指定された場合は、その値を全対象に適用する。
- [ ] **AC-05 適用不可・取消** 選択が 0〜1 件、変更指定が 0 項目、または結果に値の差分がない場合は適用できない。送信中・送信済みのフローでは適用できない。適用時に対象の存在と指定値の有効性を全件確認する。必須カスタムフィールドを変更対象にした場合は空欄・空白のみを拒否する。対象の消失や無効な値があれば理由を表示し、操作全体を拒否する。適用前の取消、適用不可、適用失敗のいずれでも、一括変更操作によるノード、履歴、下書きの更新は発生しない。
- [ ] **AC-06 全件反映と履歴** 有効な指定を適用すると、選択したノード全件に指定値と AC-04 の補正を反映する。選択外のノード、指定外の属性、ノード位置、親子関係、依存関係を保持する。変更全体を Undo 1 回で戻し、Redo 1 回で再適用できる。適用結果は既存形式の自動下書きに保存され、再読み込み時の既存サニタイズを経て復元される。
- [ ] **AC-07 起票時の検証** `[ASSUMPTION]` トラッカー変更で新たに必須となったカスタムフィールドが未入力でも、編集中の下書きとして適用できる。適用後の既存ノード検証で必須項目の不足を確認でき、一括登録は補完されるまで止まる。既存検証を通過した状態で一括登録すると、一括変更された属性が Redmine のチケットに反映される。

## 4. Public API / DB Schema

- 既存の `bootstrap` / `bulk_create` API、DB スキーマ、自動下書き・名前付き保存・JSON 入出力の形式を使用する。属性の適用時はネットワーク経由の更新を行わない。

## 5. Constraints

- **Security**　候補と適用可否の判定に、現在のプロジェクトとユーザーの Bootstrap メタデータを使用する。トラッカー・優先度・担当者・バージョンの ID、許可ステータス、カスタムフィールドの可視性・形式・選択肢を確認する。一括登録時は既存のセッション認証、権限、CSRF 保護、Redmine の属性制御に従う。
- **Performance**　一括変更の適用を 1 回の履歴操作とし、自動下書き保存は適用 1 回につき 1 回とする。

## 6. Required Tests

- 正常系 `BNE-01` 既存のタスクと親グループ枠に 6 種の属性を適用し、未選択の子タスクと他の属性・カスタムフィールドを保持する（AC-01、AC-02、AC-06）。
- 正常系 `BNE-02` 混在値から担当者・バージョン・任意カスタムフィールドを明示的に空へ変更し、未指定の値と真偽値の「いいえ」を空と区別する（AC-02）。
- 境界値 `BNE-03` 異なるトラッカー間の共通ステータス、候補が空の場合、無効な担当者・バージョン、非共通または不可視のカスタムフィールド、対象選択やトラッカー指定による候補再計算を確認する（AC-03）。
- 境界値 `BNE-04` トラッカー変更で、許可済みステータスの維持、許可された既定値への補正、明示指定による上書きを確認する。許可される既定値がない場合は全件拒否する（AC-04）。
- 失敗系 `BNE-05` 0 件・1 件、変更指定なし、差分なし、送信中・送信済み、適用直前の対象消失、無効な値、取消で、ノード・履歴・下書きに副作用がないことを確認する（AC-05）。
- 正常系 `BNE-06` 一括変更を Undo・Redo それぞれ 1 回で戻す・再適用する動作と、再読み込み後の下書き復元を確認する（AC-06）。
- 失敗系 `BNE-07` トラッカー変更で新たに必須となったフィールドが空の下書きを適用でき、既存の登録前検証が起票を止めることを確認する（AC-07）。
- **Integration / E2E**　評価用 Redmine で、キーボードによる対象選択、候補の連動、適用、Undo/Redo、再読み込み、必須エラーと補完後の一括登録を実ブラウザで確認する。選択外ノードおよび親子・依存関係も画面と起票結果で確認する。[実行手順](../06-testing-and-verification.md)
- **Regression**　Vitest は公開入口の結果を `BNE-01`〜`BNE-07` で検証する。既存の単一ノード・エッジ編集、下書き・保存済みフロー・JSON 入出力、起票時の権限・検証を回帰対象に含める。実装時にツールバーと検証シナリオの記述、[機能マップ](../../verification/feature-map.json) を更新し、`node verification/verify-cli.mjs` を実行する。
