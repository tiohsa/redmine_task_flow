# SPEC: ノードのチケット属性を一括変更

## 1. Goal

- タスクフローに追加済みの複数ノードを選び、トラッカー、優先度、担当者、対象バージョンをまとめて変更できるようにする。一括変更の適用後は、通常の編集と同じように下書きに反映し、既存の一括登録で起票できる。

## Clarifications

### Session 2026-11-23

- Q: カスタムフィールドを一括変更の対象に含めるか？ → A: カスタムフィールドの一括変更は対象外とする。

## 2. Non-goals / Out-of-scope

- 起票済み Redmine チケットの更新、複数フローをまたぐ操作、新規ノードの既定値の一括設定。
- ステータス、題名、説明、日程、工数、ノード位置、親子関係、依存関係、カスタムフィールドの一括編集。
- キャンバスの選択モデル、単一ノード・エッジの編集方法、既存のカスタムフィールド形式の対応範囲の拡張。

### 利用シナリオ

- **P1 属性をまとめて反映する（AC-01〜AC-06、AC-08）** 編集権限があり、値の異なるタスクと親グループ枠がある。利用者が両方を選択し、有効なトラッカーと担当者を指定して適用すると、選択した 2 件へ反映される。親グループ枠の子タスクを選択していなければ、その子タスクの値は変わらない。
- **P2 適用結果を戻して作業を再開する（AC-06）** 適用後に Undo を 1 回実行すると変更前に戻り、Redo を 1 回実行すると全件に再適用される。自動下書きの保存後に画面を再読み込みすると、再適用後の状態から作業を再開できる。
- **P3 一括変更後のフローを起票する（AC-07、AC-09、AC-10）** トラッカー変更で必須項目が増えた場合は、下書きへ適用した後に各ノードの編集画面で不足項目を補う。3 権限がそろい、登録前検証を通過していれば、変更後の属性で起票できる。

## 3. Acceptance Criteria

- [ ] **AC-01 対象選択** `[ASSUMPTION]` 編集可能なフローにノードが 2 件以上あるとき、ツールバーの「属性を一括変更」から対象選択と属性指定を開ける。各ノードを個別に選択・解除でき、選択件数が表示される。タスクノードと親グループ枠の混在を許可する。親グループ枠の選択で子タスクが自動選択されることはない。対象選択と適用はキーボードでも操作できる。
- [ ] **AC-02 属性の指定** `[ASSUMPTION]` トラッカー、優先度、担当者、対象バージョンを個別に変更対象へ追加できる。一括編集画面にカスタムフィールドの入力欄は表示しない。初期状態は全項目「変更しない」とし、元の値が混在していてもいずれかの値を適用値として自動選択しない。担当者は「未割当」、対象バージョンは「なし」を明示指定できる。
- [ ] **AC-03 トラッカー連動** 担当者・対象バージョンは全対象の適用後トラッカーで該当フィールドが有効な場合に変更できる。トラッカー未指定時はノードごとの現在のトラッカーを使う。トラッカーや対象選択の変更で候補を更新し、すでに指定した値が無効になった場合は該当項目を示して適用を止める。
- [ ] **AC-04 トラッカー変更時のステータス維持** `[ASSUMPTION]` 一括編集では各ノードのステータスを維持する。トラッカーが変わるすべてのノードで現在のステータスが変更先でも許可される場合は、他の適用条件を満たせば適用できる。維持できないノードが 1 件でもあれば、該当ノードと理由を表示して全件の適用を止める。変更先に既定ステータスがある場合も同じ扱いとする。
- [ ] **AC-05 適用不可・取消** 選択が 0〜1 件、変更指定が 0 項目、または結果に値の差分がない場合は適用できない。ノードが 0〜1 件のフローでは一括編集を開けない。開いた直後および全選択を解除した後は選択件数を 0 件と表示し、「適用」を無効にする。送信中・送信済みのフローでは適用できない。適用前に取り消すと指定を破棄し、一括編集を閉じる。適用前の取消、適用不可、適用失敗のいずれでも、一括変更操作によるノード、履歴、下書きの更新は発生しない。
- [ ] **AC-06 全件反映と履歴** 有効な指定を適用すると、選択したノード全件に指定値を反映する。選択外のノード、指定外の属性、ノード位置、親子関係、依存関係を保持する。カスタムフィールドの既存値は一括適用時に変更しない。変更全体を Undo 1 回で戻し、Redo 1 回で再適用できる。適用結果は既存形式の自動下書きに保存され、再読み込み時の既存サニタイズを経て復元される。その際、復元時のトラッカーで無効なカスタムフィールドの値は既存の処理により除外される。
- [ ] **AC-07 起票時の検証** `[ASSUMPTION]` トラッカー変更で新たに必須となったカスタムフィールドが未入力でも、編集中の下書きとして適用できる。適用後の既存ノード検証で必須項目の不足を確認でき、一括登録は各ノードの編集画面で補完されるまで止まる。既存検証を通過した状態で一括登録すると、一括変更された属性が Redmine のチケットに反映される。
- [ ] **AC-08 選択件数の上限** `[ASSUMPTION]` 一括変更 1 回の上限は 100 件とし、タスクと親グループ枠をそれぞれ 1 件と数える。有効な変更を指定した 100 件の選択は全件に適用できる。101 件以上を選択した場合は、選択件数と上限を表示し、全件の適用を止める。100 件以下に選び直し、他の適用条件を満たせば適用できる。上限の判定には選択中のノードを数える。一括登録では既存どおり、フロー全体の起票対象を数える。
- [ ] **AC-09 権限不足** 「タスクフローからの一括起票」「チケットの追加」「チケットの関連の管理」のいずれかが対象プロジェクトで不足する場合、タスクフローメニューを表示せず、画面を直接開いても利用を拒否する。編集画面を開いた後に権限が取り消され、一括登録が拒否された場合は、権限不足を表示する。チケット・関連の作成は 0 件とし、フローを送信済みにせず、編集済みの内容と下書きを保持する。
- [ ] **AC-10 失敗からの修正** 適用時に対象の存在と値の有効性を全件確認する。適用直前に消失したノードや、許可されない指定値が 1 件でもあれば該当する対象または項目と理由を示し、全件の適用を拒否する。件数違反や直前の保存失敗があっても、現在の対象・項目別の理由を表示する。画面を開いたまま対象や値を修正して再試行できる。一括登録でチケットまたは関連の保存が失敗した場合は同じノードに対する複数の詳細を含め、既存のエラー詳細を表示する。作成結果は 0 件とする。編集中の内容を保持し、修正後に再登録できる。

### 成功指標

- 有効な変更を 100 件へ 1 回の適用で反映でき、Undo 1 回で 100 件すべてが元に戻る。
- 選択件数が 0 件、1 件、101 件以上、または適用検証で 1 件以上のエラーがある場合、一括変更で更新されるノードは 0 件となる。
- 必要な 3 権限のうち 1 つでも不足する場合、作成されるチケットと関連はともに 0 件となる。

### 前提と対象データ

- 利用者は対象プロジェクトでタスクフローを使う担当者とする。対象データは編集中のフローのタスクノードと親グループ枠、そのチケット属性、自動下書きと操作履歴とする。
- 1 回の選択上限には、既存の一括登録でチケットとして扱える件数と同じ 100 件を採用する。[一括登録仕様](../05-persistence-and-bulk-create.md)
- 画面を開いた後の権限変更は、一括登録時に現在の権限で判定する。属性の適用と下書きへの反映は、編集中のフロー上で完結する。

## 4. Public API / DB Schema

- 既存の `bootstrap` / `bulk_create` API、DB スキーマ、自動下書き・名前付き保存・JSON 入出力の形式を使用する。属性の適用時はネットワーク経由の更新を行わない。

## 5. Constraints

- **Security**　候補と適用可否の判定に、現在のプロジェクトとユーザーの Bootstrap メタデータを使用する。トラッカー・優先度・担当者・対象バージョンの ID と、適用後トラッカーでの担当者・対象バージョン欄の有効性を確認する。トラッカー変更時は、現在のステータスが変更先でも許可されるか確認する。一括登録時は既存のセッション認証、権限、CSRF 保護、Redmine の属性制御に従う。
- **Performance**　一括変更の適用を 1 回の履歴操作とし、自動下書き保存は適用 1 回につき 1 回とする。
- **保存失敗**　下書きの書き込み失敗時は理由をダイアログに表示し、ノードと Undo/Redo 履歴を保持する。ダイアログの選択と指定値はそのまま再試行に使える。

## 6. Required Tests

- 正常系 `BNE-01` 既存のタスクと親グループ枠に対象の 4 種の属性を適用する。一括編集にステータスとカスタムフィールドの入力欄がなく、選択したノードのステータスとカスタムフィールドの既存値、未選択の子タスク、指定外の属性を適用時に保持することを確認する（AC-01、AC-02、AC-06）。
- 正常系 `BNE-02` 混在値から担当者を「未割当」、対象バージョンを「なし」に変更でき、指定しなかった項目の元の値を保持することを確認する（AC-02）。
- 境界値 `BNE-03` 無効な担当者・対象バージョンの ID、適用後トラッカーでの担当者・対象バージョン欄の無効化、対象選択やトラッカー指定による候補の更新を確認する（AC-03）。
- 境界値 `BNE-04` 現在のステータスが全件で変更先トラッカーに許可される場合は、各ステータスを保持して適用する。許可されないノードが 1 件でもある場合は、変更先に既定ステータスがあっても対象と理由を表示して全件の適用を拒否し、ノード・履歴・下書きが更新されないことを確認する（AC-04、AC-05）。
- 境界値 `BNE-05` フロー内のノードが 0 件・1 件では入口を開けず、2 件以上のフローで選択が 0 件・1 件では適用できないことを確認する。変更指定なし、差分なし、送信中・送信済み、取消でもノード・履歴・下書きが更新されないことを確認する（AC-05）。
- 正常系 `BNE-06` 一括変更を Undo・Redo それぞれ 1 回で戻す・再適用する動作と、再読み込み後の下書き復元を確認する。復元時はトラッカーで有効なカスタムフィールドの値が残り、無効なカスタムフィールドの値が既存の処理で除外されることを確認する（AC-06）。
- 失敗系 `BNE-07` トラッカー変更で新たに必須となったカスタムフィールドが空でも下書きに適用できることを確認する。既存の登録前検証で起票が止まり、対象ノードの編集画面で補完すれば起票できることを確認する（AC-07）。
- 境界値 `BNE-08` 親グループ枠を含む 101 件以上のフローで 99 件と 100 件の選択を各 1 回で適用でき、101 件の選択では件数と上限が表示され、ノード・履歴・下書きが更新されないことを確認する。100 件へ戻すと全件に適用できる（AC-08）。
- 境界値 `BNE-09` 3 権限をそれぞれ 1 つずつ欠いた利用者でメニュー非表示と画面への直接アクセス拒否を確認する。編集画面を開いた後の権限取り消しによる登録拒否では、権限不足の表示、作成 0 件、送信済みへの遷移なし、編集内容と下書きの保持を確認する（AC-09）。
- 失敗系 `BNE-10` 適用直前の対象消失と無効な指定値を個別に確認する。理由が示され、全件が拒否され、ノード・履歴・下書きが更新されず、修正後に再適用できることを確認する（AC-05、AC-10）。
- 失敗系 `BNE-11` 一括登録の保存に失敗したとき、エラー詳細を表示し、チケットと関連を 1 件も作成せず、編集内容を保持して再登録できることを確認する（AC-10）。
- **Integration / E2E**　評価用 Redmine で、キーボードによる対象選択、候補の連動、適用、Undo/Redo、再読み込み、0 件・上限・上限超過、権限不足、必須エラーと補完後の一括登録を実ブラウザで確認する。選択外ノードおよび親子・依存関係も画面と起票結果で確認する。[実行手順](../06-testing-and-verification.md)
- **Regression**　フロントエンドは Vitest、登録時の権限とロールバックは Minitest で、`BNE-01`〜`BNE-11` の各ケースを公開入口から検証する。既存の単一ノード・エッジ編集、下書き・保存済みフロー・JSON 入出力、起票時の権限・検証を回帰対象に含める。実装時にツールバーと検証シナリオの記述、[機能マップ](../../verification/feature-map.json) を更新し、`node verification/verify-cli.mjs` を実行する。
